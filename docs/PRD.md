# PRD — Obsidian Study Session Tracker

**Status:** Draft v0.1
**Author:** (you)
**Last updated:** 2026-10-20
**Target:** Obsidian community plugin, with a local MCP server as a fast-follow

---

## 1. Summary

An Obsidian plugin that tracks a focused **study session** — you start it, work through your
vault, and stop it — and then writes an intelligent summary of what you learned into that day's
daily note, inside a clearly demarcated block.

Summaries are generated by the **Claude API** (user supplies their own key). When no key is
present or a call fails, the plugin falls back to a deterministic **template summary** so the core
loop always works offline.

The capture layer, the summarizer, and the output ("sink") are deliberately separated so that
later additions — a local MCP server, a Chrome extension, web-search context, and sharing/publishing —
plug into the same session record without reworking the core.

---

## 2. Goals

- Let a user explicitly **start and stop** a study session.
- **Capture vault activity** during the session (notes opened/created/modified, time per note,
  links followed, tags touched).
- On stop, write a **smart summary** of the session into the **daily note**, inside a demarcated,
  machine-findable block.
- Generate that summary via the **Claude API (BYO key)**, degrading gracefully to a **template
  summary** when unavailable.
- Be **publishable to the Obsidian community plugin store**.
- Keep the codebase **modular**, so future signal sources and sinks attach to a stable session schema.

## 3. Non-goals (for v1)

- Inferred / automatic session boundaries (idle detection). v1 is explicit start/stop only.
- Capturing anything outside the vault: external browser activity, web searches, PDF reading
  position. These are deliberately deferred to later phases (Chrome extension, web-search MCP).
- Mobile-specific features beyond "it shouldn't break on mobile."
- Sharing / publishing to an audience. Architected for, but out of scope for v1 (see §10).

---

## 4. Users & motivation

- **Primary user:** you — someone doing deliberate, self-directed study inside Obsidian who wants
  an automatic record of each session without manual note-keeping.
- **Secondary users:** other Obsidian users with a daily-note habit who want effortless session logs.
- **Later consumer:** Claude Code, reading session context through the local MCP server.

### User stories (v1)
- *As a learner,* I can run "Start study session" so the plugin begins recording my activity.
- *As a learner,* I can run "Stop study session" and immediately see a summary appended to today's
  daily note in a tagged block.
- *As a learner,* I can provide my Claude API key in settings to get intelligent prose summaries.
- *As a privacy-conscious user,* if I provide no key, I still get a useful template summary and
  nothing leaves my device.
- *As a user,* I can see what the plugin captured (notes touched, time, links) in the block, not
  just prose.

## 5. Architecture

The design has three layers connected by one contract — the **session record**.

```
[ Signal Sources ]            [ Core ]                 [ Sinks ]
  Obsidian activity  ──┐                           ┌── Daily-note writer
  Chrome ext (later) ──┼──>  Session Store   ──>   ┼── MCP server (later)
  Web-search (later) ──┘     (structured          └── Share/publish (later)
                             session records)
                                   │
                                   ▼
                             Summarizer (pluggable backend)
                              ├─ Claude API  (default, BYO key)
                              └─ Template    (fallback)
```

### Modular seams
1. **Signal source → Session Store.** Sources emit events into the store; the store doesn't care
   where they came from. v1 has one source (Obsidian). Chrome/web-search add sources later without
   touching the store.
2. **Session record → Summarizer.** A single `Summarizer` interface: `summarize(record) → markdown`.
   Three backends implement it (Claude API, template, and later MCP-driven). The caller never
   branches on backend.
3. **Summary → Sink.** Sinks consume `{record, summary}`. v1 has one sink (daily-note writer). MCP
   server and share/publish are future sinks reading the same data.

Get these three contracts right and every roadmap item attaches without a rewrite.

## 6. The session record (core contract)

Stored as JSON. One record per session. **Storage location:** plugin-private data under
`.obsidian/plugins/today-i-learnt/sessions/` (tidier than vault-visible files; keeps the
vault clean). The MCP server (v1.2) reads these files from disk.

```json
{
  "id": "2026-10-20T09:03:12-session",
  "start": "2026-10-20T09:03:12+05:30",
  "end": "2026-10-20T09:51:40+05:30",
  "durationSec": 2908,
  "events": [
    { "ts": "...", "source": "obsidian", "type": "note.open",   "path": "Topics/Transformers.md" },
    { "ts": "...", "source": "obsidian", "type": "note.modify", "path": "Topics/Transformers.md", "bytesDelta": 740 },
    { "ts": "...", "source": "obsidian", "type": "note.create", "path": "Daily/scratch.md" },
    { "ts": "...", "source": "obsidian", "type": "link.follow", "from": "A.md", "to": "B.md" },
    { "ts": "...", "source": "obsidian", "type": "tag.touch",   "path": "A.md", "tag": "#attention" }
  ],
  "sources": ["obsidian"],
  "derived": {
    "notesTouched": ["Topics/Transformers.md", "..."],
    "created": ["Daily/scratch.md"],
    "timePerNoteSec": { "Topics/Transformers.md": 1200 },
    "tagsTouched": ["#ml", "#attention"],
    "linksFollowed": 1
  },
  "summary": {
    "backend": "claude-api",
    "markdown": "...",
    "generatedAt": "2026-10-20T09:51:45+05:30"
  }
}
```

**Design note:** the record stores file *paths* and the generated *summary* durably. That is the
only thing the future share/publish phase needs from v1 — so no schema change is required later.

### Event schema rules
- **Event `type` names what happened, not who reported it.** Types are named after the thing acted
  on (`note.open`, `link.follow`), so any source that observes the same thing emits the same type,
  and consumers (derive, summarizers, sinks) never branch on source.
- **Every event carries `source`** (`"obsidian"`, later `"chrome"`, `"web-search"`) for provenance
  and debugging only. The record lists contributing sources in `sources`.
- **New sources add new types** (e.g. `page.visit`, `search.query`) rather than renaming existing
  ones. Consumers ignore types they don't recognise, so older code keeps working.
- **Events hold only plain JSON values** (strings, numbers) — never platform objects such as
  Obsidian's `TFile`. This keeps records portable to the MCP server and other tools.
- Each event type has a fixed set of required fields (modelled in code as a TypeScript
  discriminated union in `src/types.ts`).

## 7. Capture signals (v1 scope)

Available through the Obsidian plugin API and in scope:
- `note.open` / `note.create` / `note.modify` / `note.rename` / `note.delete`
- active-leaf changes → **time per note**
- `link.follow` (navigation between notes)
- `tag.touch` (tags added/edited)

Explicitly **out of scope for v1** (document this to set expectations):
- PDF reading position, external browser activity, web searches, anything outside the vault.

---

## 8. Output: the daily-note study block

Written on session stop into the configured daily note. Uses Obsidian comment markers (`%% %%`) as
machine-findable anchors so the block can be located and rewritten precisely, with a `[!study]`
callout as the human-facing part.

```markdown
%% study-session:start id=2026-10-20T09:03 %%
> [!study] Study session · 09:03–09:51 · 48m
> **Topics:** Transformers, Attention
> **Notes:** 6 touched, 2 created
>
> <Claude-generated summary prose here>
%% study-session:end %%
```

- The `%% ... %%` markers delimit a region the plugin (and later the MCP server) can find and
  replace without disturbing the rest of the daily note.
- The `id=` ties the block back to its session record.
- If the daily note doesn't exist yet, create it following the Daily Notes / Periodic Notes
  location & format settings where detectable; otherwise fall back to a configured path.

## 9. Summarization

### Interface
```
interface Summarizer {
  summarize(record: SessionRecord): Promise<string /* markdown */>;
}
```

### Backends
| Backend | When used | Network | Notes |
|---|---|---|---|
| **Claude API** | Default, when a key is set | Opt-in | Sends session note content to Anthropic. |
| **Template** | No key, or API failure | None | Deterministic: counts, topics, time, links. |
| **MCP-driven** | v1.2 | Local | Claude Code reasons and calls `write_summary`. |

### Claude API backend — requirements
- **BYO key**, entered in plugin settings.
- Use Obsidian's `requestUrl` (not raw `fetch`) to avoid CORS issues.
- Handle: rate limits, network errors, oversized sessions (truncate / chunk note content to fit
  context), malformed responses → on any failure, **fall back to the template backend** and note
  the fallback in the block.
- Prompt takes the session record + relevant note excerpts and returns concise markdown suitable
  for the callout.

### Template backend
- Pure function of the record. Example output: "48m across 6 notes (2 created). Focus: Transformers,
  Attention. Followed 3 links." Always works offline.

## 10. Future phases (architected for, not in v1 scope)

### Phase 2 — Local MCP server (v1.2)
Reads session records from disk and exposes them to Claude Code. Minimal tool surface:
- `list_sessions(date_range)`
- `get_session(id)`
- `write_summary(id, markdown)` — **writes only inside the demarcated study block** of the daily
  note (confirmed scope). Reuses the summarizer module.

### Phase 3 — More signal sources
- Chrome extension and a web-search MCP feed additional events into the Session Store as new
  **sources**, using the same event schema.

### Phase 4 — Share / publish (parked, but intended endgame)
Whatever is learned/read in a session should be shareable with an audience — either the **summary**
(curated) or the **source notes** (full fidelity). Modeled as additional **sinks**:
- Export a session bundle (summary + touched notes) as markdown / folder / zip.
- Publish targets: Obsidian Publish, gist, static-site export, or copy-to-clipboard.
- Toggle: share summary vs. share source notes.

The v1 session record already stores the paths and summary this phase needs — no schema change required.

## 11. Settings (v1)
- Claude API key (with a visible warning that it is stored in plugin data and will sync with the vault).
- Daily-note target behavior (auto-detect Daily/Periodic Notes vs. configured path).
- Summary verbosity / length preference.
- Toggle: include the structured capture (counts/links) in the block alongside prose.

## 12. Risks & review considerations
- **Secret storage.** The API key lives in `.obsidian/plugins/.../data.json` in plaintext and
  rides along with vault sync. Must warn clearly in settings and README.
- **Community-store review.** Network calls that send vault content to a third party draw scrutiny.
  Allowed, but requires explicit disclosure ("sends session note content to Anthropic") in README
  and settings. The template fallback helps demonstrate the plugin is useful without the network.
- **Context limits.** Long sessions can exceed the model context; need truncation/chunking.
- **Daily-note ecosystem compatibility.** Respect Daily/Periodic Notes conventions to avoid
  clobbering user notes; the comment-marker block must be idempotent (re-running updates in place).

## 14. Open questions
- Exact prompt design and how much note *content* (vs. just paths/metadata) to send to the API by default.
- Idempotency strategy when a daily note already contains a block for the same session id.
- Whether to let users review/edit the summary before it's written, or write immediately on stop.
- How to represent multiple sessions in one day in the daily note (stacked blocks vs. merged).

---

## 15. Success criteria (v1)
- Start → work → stop produces a correct, well-formatted study block in the daily note.
- With a key: summaries are genuinely useful prose. Without a key: template summary still reads well.
- Clean enough separation that the MCP server (v1.2) is additive, touching no capture code.
- Accepted into the Obsidian community plugin store.
